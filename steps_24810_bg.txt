Как се изпълнява история 24810

Поръчката е `sn_ind_tmt_orm_order`. Файловете са в `sys_attachment`. Кламерът в дясната лента качва, преглежда, тегли и трие. Табът Attachments показва същите редове.

Ново поле не се създава. На `sys_attachment` вече има `u_document_status` със стойности `internal` и `external`. Файл, качен на поръчката, се записва като `internal`. `snc_external` не вижда редове със стойност `internal`.

Кой какво прави:

- Качва и трие: `sn_ind_tmt_orm.order_admin`, `sn_ind_tmt_orm.order_agent`, `sn_ind_tmt_orm.order_fulfilment_manager`. Описанията им са писане и промяна на поръчката.
- Преглежда и тегли: всяка роля от `roles_24810.txt`.
- `snc_external` не вижда файл с `u_document_status` = `internal`.

## Стъпка 1. Един Script Include с ролите

Работи в Global, за да го викат правата.

1. `sys_script_include.list`, New.
2. Name: `OrderAttachmentAccess`
3. Client callable: изключено
4. Скрипт:

```javascript
var OrderAttachmentAccess = Class.create();
OrderAttachmentAccess.prototype = {
    initialize: function() {},

    ORDER_TABLE: 'sn_ind_tmt_orm_order',

    READ_ROLES: [
        'sn_ind_tmt_orm.fulfillment_viewer',
        'sn_ind_tmt_orm.fulfillment_writer',
        'sn_ind_tmt_orm.order_admin',
        'sn_ind_tmt_orm.order_agent',
        'sn_ind_tmt_orm.order_approver',
        'sn_ind_tmt_orm.order_creator',
        'sn_ind_tmt_orm.order_fulfilment_agent',
        'sn_ind_tmt_orm.order_fulfilment_manager',
        'sn_ind_tmt_orm.order_integrator',
        'sn_ind_tmt_orm.order_internal_contacts_user',
        'sn_ind_tmt_orm.order_internal_contact_user',
        'sn_ind_tmt_orm.order_viewer',
        'sn_ind_tmt_orm.service_order_agent',
        'sn_ind_tmt_orm.service_order_manager'
    ],

    MANAGE_ROLES: [
        'sn_ind_tmt_orm.order_admin',
        'sn_ind_tmt_orm.order_agent',
        'sn_ind_tmt_orm.order_fulfilment_manager'
    ],

    _hasAny: function(roles) {
        for (var i = 0; i < roles.length; i++) {
            if (gs.hasRole(roles[i]))
                return true;
        }
        return false;
    },

    canRead: function(attachment) {
        if (!attachment)
            return true;
        if (attachment.getValue('u_document_status') == 'internal' && gs.hasRole('snc_external'))
            return false;
        if (attachment.getValue('table_name') != this.ORDER_TABLE)
            return true;
        return this._hasAny(this.READ_ROLES);
    },

    canManage: function(attachment) {
        if (!attachment || attachment.getValue('table_name') != this.ORDER_TABLE)
            return true;
        return this._hasAny(this.MANAGE_ROLES);
    },

    isManagerOnOrder: function(attachment) {
        return !!attachment &&
            attachment.getValue('table_name') == this.ORDER_TABLE &&
            this._hasAny(this.MANAGE_ROLES);
    },

    hideFromQuery: function(current) {
        if (gs.hasRole('admin'))
            return;
        if (gs.hasRole('snc_external')) {
            var status = current.addNullQuery('u_document_status');
            status.addOrCondition('u_document_status', 'external');
            return;
        }
        if (!this._hasAny(this.READ_ROLES))
            current.addQuery('table_name', '!=', this.ORDER_TABLE);
    },

    type: 'OrderAttachmentAccess'
};
```

5. Submit.

Ако вече има поле `u_internal` и business rule, което го пълни, изтрий полето и това правило. Ползва се `u_document_status`.

## Стъпка 2. Файл на поръчката става internal

Създай правилото в **Global**. `sys_attachment` и `u_document_status` са глобални. Качването минава през глобалния attachment процесор. Правило в `sn_ind_tmt_orm` може да не тръгне при това качване и да не може да пише в глобалното поле.

1. Смени приложението горе вдясно на Global.
2. `sys_script.list`, New.
3. Попълни:

- Name: `Order attachment is internal`
- Table: `sys_attachment`
- Advanced: включено
- When: before
- Insert: включено
- Update: включено
- Filter: Table name is `sn_ind_tmt_orm_order`

```javascript
(function executeRule(current, previous) {
    current.u_document_status = 'internal';
})(current, previous);
```

4. Submit.

Стойността в скрипта е Value от choice листа, не етикетът. Ако в `sys_choice` за `sys_attachment.u_document_status` Value е различно от `internal`, сложи това Value.

Вече качени файлове на поръчки, които не са internal, пусни веднъж от Scripts - Background:

```javascript
var gr = new GlideRecord('sys_attachment');
gr.addQuery('table_name', 'sn_ind_tmt_orm_order');
var qc = gr.addNullQuery('u_document_status');
qc.addOrCondition('u_document_status', '!=', 'internal');
gr.query();
while (gr.next()) {
    gr.u_document_status = 'internal';
    gr.setWorkflow(false);
    gr.autoSysFields(false);
    gr.update();
}
```

## Стъпка 3. Read за ролите от файла

Преди правата: Elevate Roles, `security_admin`.

Ново read правило до старото не стига. Старото пуска всеки, който чете поръчката. Затова правилото е Deny unless.

1. `sys_security_acl.list`, New.
2. Попълни:

- Type: record
- Operation: read
- Name: `sys_attachment`
- Decision type: Deny unless
- Admin overrides: включено
- Requires role: празно
- Advanced: включено

3. Скрипт:

```javascript
answer = new OrderAttachmentAccess().canRead(current);
```

4. Submit.

Файл с `u_document_status` = `internal` се отказва на `snc_external`, включително по директен адрес. Файл на `sn_ind_tmt_orm_order` минава само с роля от `READ_ROLES`. Файл на друга таблица със статус `external` остава по старите права.

Ако на формата няма Decision type, мини на последната секция.

## Стъпка 4. Заявката на списъка Attachments в workspace

Средният таб Attachments е related list. Неговата заявка е relationship към `sys_attachment`. В нея се добавя филтърът за `snc_external`. Редове с `u_document_status` = `internal` не влизат в резултата. Редове `external` и празен статус остават.

1. Напиши `sys_ui_related_list.list` и натисни Enter.
2. Намери списъка за таблица `sn_ind_tmt_orm_order` и изгледа, който workspace ползва.
3. Отвори related list записа Attachments. Стойността в Related list е `REL:` плюс sys_id.
4. Отвори този запис в `sys_relationship`. Queries from table е `sys_attachment`.
5. В скрипта на relationship остави редовете, които връзват файла към поръчката. Добави само блока за ролята:

```javascript
if (gs.hasRole('snc_external')) {
    var status = current.addNullQuery('u_document_status');
    status.addOrCondition('u_document_status', 'external');
}
```

Целият скрипт, ако сега връзва само таблица и sys_id, става така:

```javascript
(function refineQuery(current, parent) {
    current.addQuery('table_name', parent.getTableName());
    current.addQuery('table_sys_id', parent.getUniqueValue());
    if (gs.hasRole('snc_external')) {
        var status = current.addNullQuery('u_document_status');
        status.addOrCondition('u_document_status', 'external');
    }
})(current, parent);
```

6. Update.

Същият филтър стои и в query business rule, за да важи и извън този related list. Ако правилото от долния скрипт вече е създадено, смени метода `hideFromQuery` в Script Include с версията от стъпка 1 и обнови правилото.

1. `sys_script.list`, New, ако правилото го няма.
2. Попълни:

- Name: `Hide internal attachments from snc_external`
- Table: `sys_attachment`
- Advanced: включено
- When: before
- Query: включено
- Insert, Update, Delete: изключени
- Application: Global

```javascript
(function executeRule(current, previous) {
    new OrderAttachmentAccess().hideFromQuery(current);
})(current, previous);
```

3. Submit.

Потребител с `snc_external` в таб Attachments не вижда редове internal. Потребител с роля от `roles_24810.txt` ги вижда.

## Стъпка 5. Качване и изтриване

Остани в Global и с вдигната роля `security_admin`. Правят се четири отделни записа в `sys_security_acl`. Requires role на четирите е празно. Ако там се сложат трите роли, ServiceNow иска потребителят да ги има всичките наведнъж. Кой от трите мениджъра минава се решава в скрипта.

Качват и трият само `sn_ind_tmt_orm.order_admin`, `sn_ind_tmt_orm.order_agent` и `sn_ind_tmt_orm.order_fulfilment_manager`. Останалите роли от `roles_24810.txt` преглеждат и теглят.

### 5.1 Delete, Deny unless

1. Напиши `sys_security_acl.list` и натисни Enter.
2. Натисни New.
3. Попълни:

- Type: record
- Operation: delete
- Name: `sys_attachment`
- Decision type: Deny unless
- Admin overrides: включено
- Requires role: празно
- Advanced: включено
- Description: `Order attachment delete deny unless`

4. В Script постави:

```javascript
answer = new OrderAttachmentAccess().canManage(current);
```

5. Натисни Submit.

Това правило спира триенето, когато файлът е на `sn_ind_tmt_orm_order` и потребителят няма нито една от трите роли. Файл на друга таблица не се спира оттук.

### 5.2 Create, Deny unless

2. Попълни същите полета като в 5.1, със тези две разлики:

### Менюто на файла в десния панел

Трите реда в жълтото меню са трите операции:

- Download е read. Вижда го всяка роля от `roles_24810.txt`.
- Delete е delete. Виждат го само `order_admin`, `order_agent` и `order_fulfilment_manager`.
- Rename е write. Виждат го същите три роли.

`order_viewer` и останалите роли без тези три виждат само Download. `snc_external` не вижда самия файл, когато статусът е `internal`, и менюто не се отваря.

Провери с Impersonate на `sn_ind_tmt_orm.order_viewer`: менюто на `test1.txt` има само Download. С `order_agent` има Download, Delete и Rename.

Ако при `order_viewer` Delete или Rename още стоят, панелът не чете правата, а `AttachmentSecurity`. Дублирай include-а като `CustomAttachmentSecurity` и в `canDelete` и `canWrite`, преди копираната логика, сложи:

```javascript
if (!new OrderAttachmentAccess().canManage(current))
    return false;
```

В `canRead` сложи:

```javascript
if (!new OrderAttachmentAccess().canRead(current))
    return false;
```

Насочи read, write и delete правилата, които викат `AttachmentSecurity`, към `CustomAttachmentSecurity`.

След шестте Submit в `sys_security_acl.list` филтрирай Name is `sys_attachment`. Новите редове са create, delete и write, всеки с Deny unless и Allow if. До тях остава read правилото от стъпка 3.

## Стъпка 5а. След качване списъкът се обновява сам

Жълтият бутон над таб Attachments е Refresh на related list-а. Десният панел и този списък са два отделни компонента и качването от `+` не натиска Refresh. Връзваш събитието от панела към същото обновяване.

1. Now Experience Framework > UI Builder.
2. Experience **CSM/FSM Configurable Workspace**, страница **Record**, вариантът на `sn_ind_tmt_orm_order`.
3. В дървото отляво отвори компонента на десния панел Attachments. Това е панелът с `+`.
4. Вдясно отвори Events.
5. Add event mapping за **Attachment upload succeeded**.
6. За target избери списъка Attachments в средата на страницата, действието **Refresh**. Това е същото действие като жълтия бутон. Save.

Повтори mapping-а и за **Attachment delete succeeded** към същия Refresh. Иначе след изтриване от панела редът остава в средния списък, докато някой не натисне жълтия бутон.

Ако в target няма средния списък, панелът е в отделна подстраница и събитието не стига до него. Тогава:

1. На страницата Record създай Client script с име `Refresh order attachments list`.
2. Скрипт:

```javascript
function handler({api}) {
    api.emit('RECORD#RELATED_LIST_REFRESH_REQUESTED', {
        relatedListName: 'REL:PASTE_THE_RELATED_LIST_VALUE'
    });
}
```

3. Стойността на `relatedListName` я копираш от конфигурацията на средния Attachments списък в UI Builder. Полето е related list. За relationship изглежда като `REL:` и sys_id. Не пиши етикета Attachments.
4. Ако страницата има Dispatched events и там няма **Related list refresh requested**, добави го. Иначе `api.emit` се игнорира.
5. На десния Attachments компонент вържи **Attachment upload succeeded** и **Attachment delete succeeded** към този client script.

Проверка: качи файл от `+`. Средният таб показва новия ред с Document Status internal, без натискане на жълтия бутон. Изтрий го от панела. Редът изчезва и от таба.

## Стъпка 6. Провери

Приготви един PNG и един PDF.

1. С потребител, който има `sn_ind_tmt_orm.order_agent`, отвори поръчка и качи двата файла от кламера.
2. Прегледай PNG. Изтегли PDF и го отвори.
3. В таб Attachments и двата реда са там, Document Status е internal.
4. Изтрий PNG. Редът изчезва от панела и от таба.
5. Същото качване и изтриване минава с `sn_ind_tmt_orm.order_admin` и с `sn_ind_tmt_orm.order_fulfilment_manager`.
6. С `sn_ind_tmt_orm.order_viewer` прегледай и изтегли PDF. В менюто на файла има само Download. Delete и Rename ги няма.
7. С потребител, който има `snc_external` и няма роля от `roles_24810.txt`, отвори поръчката в портала. Файлът го няма.
8. Същият потребител отваря `/sys_attachment.do?sys_id=<sys_id на pdf>` и `/api/now/attachment/<sys_id>/file`. И двата адреса се отказват.
9. Същият потребител отваря файл на друга таблица със статус `external`. Той се отваря, ако и досега е имал достъп до него. Файл със статус `internal` остава скрит.

## Историята е готова, когато

- `order_agent`, `order_admin` и `order_fulfilment_manager` качват, преглеждат, теглят и трият
- останалите роли от `roles_24810.txt` преглеждат и теглят
- качен файл на поръчката има `u_document_status` = `internal`
- `snc_external` не вижда файл със статус `internal` и не го отваря по адрес

## Ако snc_external все пак сваля файла

Свалянето вика `AttachmentSecurity.canRead`. Ако стъпка 6.8 върне файла, дублирай include-а. Новото име и `type` са `CustomAttachmentSecurity`. Най-отгоре в `canRead`, преди копираната логика:

```javascript
if (!new OrderAttachmentAccess().canRead(current))
    return false;
```

Намери read правилото, чийто скрипт вика `AttachmentSecurity`, и го насочи към `CustomAttachmentSecurity`.
